A pipeline can check a scenario before it calls a model, then run the evaluation and retain a report for review. Start with a small scenario you understand; expand the gate once you know what a failure means for your team.

## What does the runner need?

The CLI requires Bun even when installed with npm. The 0.6.4 release qualification used Bun 1.3.10 and CLI 0.6.3. The job also needs a checked-in scenario, access to the configured provider and its secret, and network access to that provider. Model calls can incur charges and results can vary between runs. Pin the CLI and runtime versions your team has tested.

## Validate before calling a provider

```bash
akit validate scenarios/ --strict
```

Validation checks the scenario without making a model call. `--strict` treats warnings as errors. Fix an invalid scenario before investigating an evaluation result.

## Run an evaluation in GitHub Actions

This example assumes `scenarios/` contains valid scenarios configured for OpenAI and that `OPENAI_API_KEY` is available as a repository secret. Configure the secret in GitHub; do not put a key in the file. Review your repository’s rules for exposing secrets to pull requests, especially those from forks.

```yaml
name: ArtemisKit evaluation
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
jobs:
  evaluate:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
        with:
          bun-version: '1.3.10'
      - name: Install ArtemisKit
        run: bun add -g @artemiskit/cli@0.6.3
      - name: Validate scenarios
        run: akit validate scenarios/ --strict
      - name: Run evaluation
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
        run: akit run scenarios/ --ci --export junit --export-output ./test-results
      - name: Keep JUnit reports
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: artemiskit-junit
          path: test-results/*.xml
          if-no-files-found: warn
```

The run command exits nonzero when a scenario fails or execution encounters an error. A successful run means the declared checks passed for the evaluated cases and configuration; it does not establish safety or correctness for all inputs. Inspect the report and any provider or configuration errors before deciding what to change. A report might not exist if execution stops before export.

## Where should results and secrets go?

JUnit exports are written to the directory supplied by `--export-output`; filenames include the run ID. The CLI also saves manifests through its configured storage, which may be outside the export directory. Configure and collect the location your team actually uses. Reports and artifacts can contain prompts or responses: use approved test data, appropriate access and retention controls, and review redaction settings before sharing.

For more options, see the [run command](/docs/cli/commands/run/) and [validate command](/docs/cli/commands/validate/). For a GitLab starting point, see [CI/CD pipeline examples](/docs/examples/ci-cd-integration/).
